## 1. 品質ゲート（何を「収録済み」と呼ぶか）

### 1.1 原則
- ゲートは **事実項目の有無** で決める。文字数・信頼度・写真の有無では決めない（写真は「図版未収録」で別管理）。
- 判定関数は 1 つ（`recordGate(entry)` を `archive.js` に置き `window.recordGate` で公開）。台帳・詳細・サイトマップ・管理画面が同じ関数を呼ぶ。
- 投稿はブロックしない。フォーム送信時に「この登録は未収録扱いになります（不足: 作出者）」と警告だけ出す（投稿摩擦を増やさない。Hybrid の交配式必須は現行どおり）。
- プレースホルダ記録（`source_type: 'none'` / `trust: 20` / `body` が `ai_pending_origin` 文言）は **記録なし** と同じに扱う。

### 1.2 区分ごとの必須項目

| 区分 | 収録済みの条件（すべて満たす） | 参照するフィールド |
|---|---|---|
| 原種（記載種） | (a) 記載者 **かつ** 発表年 (b) タイプ産地 または 分布 のどちらか (c) 出典 URL 1件以上 | `structured.author_name`, `publication_year`, `type_locality`, `known_habitats`, `citation_links[]` または `origin.source_url` |
| 原種（sp./aff./cf.、`species_qualifier` あり） | (a) `locality`（産地・入手元）**かつ** (b) 次のいずれか: `closest_species` / `introduced_by` / 補足 40 字以上 / `species_status` が設定済み | `cultivars.locality`, `structured.closest_species`, `introduced_by`, `notes`, `species_status` |
| Hybrid | (a) 親 A・B が両方ある、**または** `formula_status ∈ {unknown, complex}` が明示 (b) 作出者 または 命名者 または 命名年 のいずれか (c) 出典 URL / 補足 80 字以上 / 投稿者＝作出者（`structured.breeder` が投稿者名と一致）のいずれか | `parent_a_text/id`, `parent_b_text/id`, `formula_status`, `structured.breeder`, `namer`, `naming_year`, `citation_links`, `notes` |
| Clone | 次のうち **2 つ以上**: 命名者/作出者、命名年、親 A/B または `selected_from_id`、補足 80 字以上、出典 URL | 同上 + `selected_from_id` |
| Seedling | 親 A・B（または「不明」明示）**かつ** 播種日 **かつ** 作出者 | `parent_*`, `structured.sowing_date`, `breeder` |

判定は非 formula の origin のうち **最も信頼度の高い 1 件**と `cultivars` 列を合わせて見る（複数記録があれば OR で拾ってよい）。

### 1.4 「未収録」の表示
- **台帳（属ページ・索引）**: 信頼度 % の代わりに mono の `未収録` ラベル（英語 `not recorded`）。行は消さない（投稿導線として残す）。
- **詳細ページ**: 標本ラベルは持っている項目だけ出す（現行どおり `cell()` が空をスキップ）。由来本文ブロックの位置に「記録未収録 — 記録を追加する」（`t('record_missing')` 新設。既定文言は BOARD §5 の決定どおり）とボタン（`data-nav="contribute"` + 編集モード）。`updateMeta({ noindex: true })` を付ける。

- **属カードの件数**: 収録済みのみ数える（「収録品種 28」）。未収録は「+1 未収録」と併記。
- **管理画面**: 「未収録一覧」タブ（不足項目つき）。オーナーがここから埋める。

### 1.5 AI 単独・信頼度 40 未満の扱い（決定: 既定で折り畳み）
条件: 非 formula の origin がすべて `author.isAI === true`（または `source_type ∈ {ai_research, ai_verified, none}`）**かつ** 最大 trust < 40 **かつ** §3 の検証済でない。
- 詳細ページでは origin カードを `<details>` で閉じ、summary に「AI 下書き（未検証・信頼度 23%）— 出典を知っている方は記録を追加してください」。中身は現行のカードそのまま（投票ボタン含む）。
- ゲート合格でも折り畳む（ゲートは「項目がある」、折り畳みは「人が裏付けていない」で別軸）。
- 非表示にしない理由: 出典 URL と投票 UI が消えると訂正の入口が無くなる。そのまま表示しない理由: 由来の正確性＝信頼（判断基準②）で、D tier 本文を一等地に出すと誤情報の拡散元になる。
- 検証済（§3）または人の記録（`manual` / `user_verified`）が 1 件でもあれば折り畳まない。

### 1.6 実装メモ
- `recordGate(entry)` の戻り値 `{ ok: boolean, missing: string[], aiOnlyLow: boolean }`。`missing` のキーは `translations.json` に `gate_missing_author`, `gate_missing_year`, `gate_missing_locality`, `gate_missing_source`, `gate_missing_parents`, `gate_missing_breeder`, `gate_missing_sowing` を追加。
- 呼び出し箇所: `archive.js` `toLedgerItems` / `renderSpecimen`、`pages.js` `renderOriginsInner`（本文ブロック）と `renderDetail`（`updateMeta` の `noindex`）、`app-core.js` 属カード件数（`genus-card__count`）、`admin.html`。
- 新規翻訳キー: `record_missing`（記録未収録 — 記録を追加する / Not yet recorded — add a record）、`ai_draft_summary`（AI 下書き（未検証・信頼度 {pct}%）/ AI draft (unverified, {pct}%)）、`ledger_not_recorded`（未収録 / not recorded）。

- 表示: 系統ブロックの親の横に「異説あり」チップ。その下に `alt_claims` を「説 / 出典」の 2 列で列挙。主説は `parent_a/b` の値、副説は alt_claims。

- 信頼度: disputed の記録は表示上の上限 60（`getTrustClass` の前で clamp。DB 値は変えない）。§3 の検証で解除。

### P6. Phase B（10 月、変更なし）

## 3. 検証ワークフロー（未記載名・暫定名・異説のある親）

### 3.1 用語
- **検証済（verified）**: 管理者が出典を確認し、その時点の記載を「サイトとして支持する」と印を付けた状態。**同定の確定ではない**。未記載名では「名前の状態（未記載 / 暫定名 / 未解決）と産地・導入経緯が出典と一致している」ことを指す。
- **コミュニティ評価**: 既存の賛成/反対投票（ログイン必須、1 人 1 票、`cast_origin_vote`）。
- **異説あり（disputed）**: 一次資料が食い違う。検証済にはできる（「食い違いがあることを確認した」の意味）。

### 3.2 誰が何をできるか

| 操作 | 誰が | 仕組み |
|---|---|---|
| 記録の追加（出典つき） | ログインユーザー全員 | 既存 `append_origin` |
| 投票 | ログインユーザー全員（自分の投稿にも可） | 既存 `cast_origin_vote` |
| 検証済にする / 外す | **管理者のみ**（`is_admin()`）。将来 `app_metadata.role='reviewer'` を同じ関数で許可（1 行追加） | 新 RPC `set_cultivar_verification` |
| 異説を書く | 管理者のみ | P5 |
| 自分の投稿を検証済にする | 不可（管理者でも自分が投稿者の記録は `note` に「自己投稿」と自動付記） | RPC 内で `user_id = auth.uid()` を見る |

支援者バッジは検証権限を持たない（金銭と正確性を分ける。BOARD §2 の特典に含めない）。

### 3.3 データと SQL（1 セッションで終わる最小構成）
```sql
alter table public.cultivars
  add column if not exists verified_at timestamptz,
  add column if not exists verified_by uuid references auth.users(id) on delete set null,
  add column if not exists verification_note text;   -- 「出典 A と B を確認。B の綴りは旧」など 200 字まで

create or replace function public.set_cultivar_verification(p_id bigint, p_verified boolean, p_note text default null)
returns jsonb language plpgsql security definer set search_path = public as $$
declare v_owner uuid;
begin
  if not public.is_admin() then return jsonb_build_object('success', false, 'error', 'Permission denied'); end if;
  select user_id into v_owner from cultivars where id = p_id;
  if p_verified then
    update cultivars set verified_at = now(), verified_by = auth.uid(),
      verification_note = left(coalesce(p_note, '') || case when v_owner = auth.uid() then '（自己投稿）' else '' end, 200)
    where id = p_id;
  else
    update cultivars set verified_at = null, verified_by = null, verification_note = null where id = p_id;
  end if;
  return jsonb_build_object('success', true);
end $$;
grant execute on function public.set_cultivar_verification(bigint, boolean, text) to authenticated;
```
`cast_origin_vote` に 1 行追加: 対象 cultivar の `verified_at is not null` なら **票は数えるが trust を更新しない**（`v_new_trust := v_current_trust`）。検証済の信頼度が群衆で下がらない代わりに、反対が賛成を 3 票以上上回り総数 5 以上になったら `verification_note` の先頭に `[要再確認]` を付けて管理画面の「再確認キュー」に出す（同じ関数内で `update`）。

`app-core.js:2716` の select に `verified_at, verified_by, verification_note` を追加し `_verifiedAt` などに載せる。

### 3.4 表示
- 標本ラベル最終行（`renderSpecimen`）に「検証状況」を必ず 1 行:
  - 検証済: `✓ 検証済 2026-09-05 — 出典 A・B を確認`（mono、`verification_note` を続ける）
  - 未検証で賛成 ≥ 3 かつ 賛成 > 反対: `コミュニティ評価 賛成 n / 反対 m`
  - それ以外: `未検証`
  - `name_status='disputed'` は末尾に `／ 異説あり`
- §1.5 の折り畳みは検証済なら解除。P5 の上限 60 も解除。
- 台帳の信頼度 % の右に検証済は `✓` を 1 文字（5 色バッジは作らない。BOARD §5）。
- 管理画面: 各記録に「検証済にする / 外す」ボタンと note 入力、「再確認キュー」「未収録一覧」の 2 タブ。

### 3.5 未記載名・暫定名の運用手順（管理者向け、そのまま `guide` に載せる）
1. 投稿時に sp./aff./cf. を選ぶと `species_qualifier` と `name_status='informal'` が自動で入る（P2）。名前は `Anthurium sp. "Fort Sherman"` 形式に自動整形。
2. AI 調査は未記載経路（`buildUndescribedSpeciesPrompt`）。Tier は引用 URL のドメインで決まる（`tierFromUrls`）。B（aroid.org / exoticaesoterica / exoticrainforest）以上なら検証候補、C（導入ナーセリー・ブリーダー本人）は「導入の証言」として採用、D（マーケットプレイス）は不採用。
3. 管理者が出典を開いて確認 → `set_cultivar_verification(id, true, '出典: …')`。**A/B tier の出典が 1 つも無い未記載名は検証済にしない**（ルールとして note に書く。RPC では縛らない）。
4. その名前が正式記載されたら（例: antolakii が Vannini & Croat で出版）: `cultivar_name` を学名に、旧暫定名と流通名（BVEP 等）を `aliases` に、`name_status='accepted'`、`species_qualifier=NULL`、`structured.species_status='described'` に変更 → 管理画面の「AI 再調査」で GBIF 経路に乗せ直す → 記載者・発表年が入ったら再度検証済に。
5. 親に異説がある Hybrid/Clone: 主説を `parent_a/b` に、副説を `alt_claims` に。両方に出典 URL が無いものは異説として載せない（推測名を作らない、の延長）。

### 3.6 参考: 現行 `cast_origin_vote` の式
`new = clamp(base + net/(total+5)·25, 5, 98)`（`20260408_vote_affects_trust.sql`）。票 1 つで ±4、10 票で最大 ±17。検証済で固定する以外は変えない。
